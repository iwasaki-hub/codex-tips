# Codexにそのまま渡せるプロンプト集

使う前に `[ ]` のプレースホルダーを置き換えてください。重要な作業ではリポジトリの既存ルールを優先します。

## 1. 読み取り調査と計画（複雑な作業向け）

```text
目的: [達成したいこと]

まず既存の実装とリポジトリの開発ルールを読み取り調査してください。
この段階ではファイルを変更しないでください。

以下を簡潔に報告してください。
1. 関連ファイルと現在の動作
2. 実装案と最小の変更範囲
3. リスク、互換性、戻し方
4. テスト・画面確認などの完成条件
5. 事前承認が必要な操作

対象外: [今回触らない機能]
```

## 2. 1機能を安全に実装

```text
目的: [機能名・期待動作]
背景: [関連画面・仕様書・現在の不具合]

制約:
- 既存の設計と対象リポジトリのAGENTS.mdを優先する
- 関係ないリファクタリング、依存追加をしない
- secretsを出力・コミットしない
- 本番変更やマージなど外部への書き込みは別途承認する

完成条件:
- [例: TypeScriptとESLintが成功]
- [例: 関連する単体テストが成功]
- [例: iPhone画面幅で横はみ出しがない]
- [例: 既存の3タブが動作する]

実装→関連する検証→失敗の修正→差分の自己確認まで進めて、
変更ファイル、実行したコマンドと結果、未確認項目を報告してください。
```

## 3. レビューのみ（実装は禁止）

```text
現在の変更差分をレビューしてください。
この段階ではコードを変更しないでください。

観点:
- バグと既存機能の退行
- 認証・RLS・秘密情報などのセキュリティ
- TypeScriptの型と境界条件
- 変更範囲の逸脱・不要な依存
- 足りないテスト、未検証の動作

各指摘に重要度、対象ファイル、理由、再現/確認方法を付けてください。
問題がなければ「見つからなかった」と書き、検証の限界を明記してください。
```

## 4. PR前の検証と報告

```text
このリポジトリの必須CIとPR運用ルールを確認してください。

変更内容に応じた関連テストに加え、PRで要求される検証を実行してください。
実行結果をPASS / FAIL / 未実施で分けて記録してください。

- 変更の要約と対象ファイル
- 型チェック、Lint、テスト、ビルドの結果
- Web確認とiPhone実機確認の区別
- リスクとロールバック案
- 機密情報や生成物の混入チェック
- マージ前に人が確認すべき事項

チェック成功を推測で記録しないでください。
```

## 5. 長期作業の引き継ぎ

```text
リポジトリの現在のブランチ、PR、コミット、差分、CI結果を確認し、
既存のWORKLOG.mdまたはHANDOFF.mdを更新してください。
同じ目的のファイルを重複して増やさないでください。

記録:
- 現在の状態（事実と未確認を区別）
- 完了した内容と未完了項目
- 重要な設計判断と理由
- 実施した検証と結果
- 次に着手する最小タスク
- 変更してはいけない箇所・安全上の注意

想像で成功やマージ済みを記載しないでください。
```

## 6. Supabase移行の事前レビュー（適用しない）

```text
SupabaseのマイグレーションとRLS変更案を読み取り専用でレビューしてください。
本番・リモートDBには適用しないでください。

確認:
- テーブル、制約、インデックス、ポリシー、GRANT
- anon / authenticated と異なるユーザー間の境界
- 既存データとの互換性
- 再実行時の動作、失敗時の復旧案
- ローカル隔離環境で必要なテスト

不足情報と未検証箇所を明記し、適用は別の承認後にしてください。
```
